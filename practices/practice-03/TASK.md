# Практическая работа 3. Одометрия и системы координат

В этой работе вы познакомитесь с оценкой движения колёсного робота и преобразованиями систем координат с помощью `tf2`. Вы сравните истинную траекторию TurtleBot3 в Webots с одометрией по энкодерам и оценкой движения по командам скорости, а также исследуете влияние шума колёсных датчиков.

## Подготовка

Практическая работа выполняется в подготовленном окружении курса с ROS2 и Webots. До занятия изучите пакет [`example_webots_odometry`](../../examples/example_webots_odometry). Запустите его и убедитесь, что робот движется по окружности. Посмотрите, как устроены сцена, локальный PROTO робота, launch-файл и скрипт `ground_truth.py`. Обратите внимание на получение истинной позы робота через супервизор, публикацию трансформов и добавление шума в показания энкодеров.

## Задание

Создайте собственный ROS2-пакет для исследования ошибки одометрии TurtleBot3 в Webots. В пакете должны быть все необходимые данные и скрипты для запуска робота (аналогично практической работе 2). Робот должен двигаться по окружности на пустой площадке со стенами. Во время движения необходимо собирать и сравнивать три оценки его позы (положения и ориентации):

1. **Ground truth (GT)** — истинную позу из симулятора, полученную через супервизор.
2. **Одометрию по энкодерам** — позу, которую рассчитывает колёсный контроллер и публикует как TF.
3. **Одометрию по командам** — позу, рассчитанную вашей программой по сообщениям `/cmd_vel` в предположении, что робот идеально выполняет команды.

Проведите три эксперимента с разным уровнем шума энкодеров. Для каждого эксперимента сохраните собранные данные и изображение с графиками траекторий и ошибок. В `README.md` приведите инструкции по запуску и небольшой анализ результатов.

### Сцена и запуск

За основу решения возьмите пакет `example_webots_odometry`. Сцена, модифицированный PROTO робота и необходимые скрипты должны находиться в вашем пакете.

Должны выполняться следующие условия:

1. В сцене есть плоская площадка со стенами, один TurtleBot3 и отдельный робот-супервизор. Других препятствий быть не должно. Размер площадки и параметры движения выберите так, чтобы робот мог двигаться по окружности без столкновений со стенами.
2. Используйте локальный файл `TurtleBot3Burger.proto` из примера. Уровень шума задавайте полем `encoderNoise` у экземпляра робота в файле сцены.
3. Супервизор с помощью отдельного скрипта должен получать истинные положение и ориентацию основного робота и публиковать динамический трансформ `map → base_link_gt`. Можно использовать скрипт из примера, изменив имя пакета при его подключении.
4. Колёсный контроллер должен публиковать трансформ `odom → base_link`, рассчитанный по энкодерам.
5. Задайте статический трансформ `map → odom`, соответствующий начальным положению и ориентации робота в глобальной системе координат сцены. Как и в примере, `map` совпадает с этой глобальной системой, а `odom` задаёт начальную систему координат колёсной одометрии.
6. Для движения периодически публикуйте в `/cmd_vel` сообщения `geometry_msgs/msg/TwistStamped` с постоянными ненулевыми `linear.x` и `angular.z`.
7. Пакет должен содержать **единый `.launch.py` файл**, который запускает симулятор с вашей сценой, контроллеры робота и супервизора, статический трансформ, публикацию команд движения и скрипт сбора данных. Ручной запуск отдельных узлов после запуска launch-файла не должен требоваться.
8. Сцена, PROTO и остальные необходимые ресурсы должны входить в устанавливаемые файлы пакета. После сборки решение должно запускаться командой `ros2 launch <имя_пакета> <имя_launch-файла>`.

### Сбор данных и расчёт траекторий

Напишите программу на Python, которая собирает данные в течение заданного времени симуляции, а после завершения этого интервала строит и сохраняет графики траекторий и ошибок. Продолжительность эксперимента задавайте параметром ROS2. Выберите её так, чтобы робот успел совершить несколько полных кругов.

Программа должна:

1. Подписываться на `/clock` для расчета времени симуляции и `/cmd_vel` для получения команд скоростей. Для получения трансформов использовать стандартные инструменты пакета `tf2` (например, `tf2_ros.Buffer` и `tf2_ros.TransformListener`).
2. Начинать записывать эксперимент, когда доступны необходимые трансформы и начинается публикация команд движения. Зафиксировать момент начала $t_0$ и начальную позу робота. Отсчитывать продолжительность эксперимента и интервалы интегрирования **по времени симуляции**, а не по системным часам компьютера.
3. Получать позу GT из ветки `map → base_link_gt`, а колёсную одометрию — из ветки `map → odom → base_link`. **Все оценки необходимо приводить к системе координат `map` стандартными средствами `tf2`**.
4. Самостоятельно рассчитывать третью траекторию, интегрируя `linear.x` и `angular.z` из полученных сообщений `/cmd_vel` по модели дифференциального робота. Между сообщениями считайте команду постоянной. Начальная поза этой оценки должна совпадать с начальной позой GT. После инициализации расчет траектории по командам должен быть независимым: нельзя подставлять в неё текущие положение или угол из GT и колёсной одометрии.
5. Сравнивать оценки позиций и ориентации с GT. Необходимо учесть, что сравнение должно происходить между максимально близкими по времени точками времени (либо можно использовать линейную интерполяцию). Учтите, что сообщения TF могут приходить в разное время.

#### Графики

Для каждого запуска сохраните **одно изображение с тремя графиками**. Для построения можно использовать `matplotlib`.

1. Три траектории на плоскости XY: GT, одометрия по энкодерам и одометрия по командам. Используйте одинаковый масштаб по осям X и Y, подпишите оси в метрах и добавьте легенду.
2. Абсолютная ошибка положения относительно GT в зависимости от времени. На графике должны быть две кривые: для одометрии по энкодерам и по командам. Ошибку рассчитывайте как евклидово расстояние на плоскости.
3. Абсолютная ошибка угла рысканья относительно GT в зависимости от времени, также с двумя кривыми.

На графиках ошибок подпишите время от начала эксперимента, ошибку положения в метрах и ошибку угла в радианах.  

### Эксперименты

Проведите **три отдельных запуска** со значениями `encoderNoise`:

- `0` — без добавленного шума;
- `0.02` рад;
- `0.1` рад.

Каждый эксперимент начинайте заново из одной и той же начальной позы. Сохраняйте одинаковые команды скорости, длительность, настройки контроллера и остальные параметры сцены; между этими тремя запусками меняйте только уровень шума.

Сохраните результаты в подпапке `results` вашего решения. Для изображений используйте различимые понятные имена, например `noise_0.png`, `noise_0_02.png` и `noise_0_1.png`.

## Подсказки и пояснения к примеру

1. **Получение ground truth.** Основному роботу в сцене задается DEF-имя `TURTLEBOT`.  В сцене создается отдельный объект `Robot`, для него задаются поля `supervisor TRUE` и `controller "<extern>"`. Launch-файл подключает к этому супервизору внешний контроллер `WebotsController`. Этот контроллер также запускает плагин (это задается файлом `resource/ground_truth_supervisor.urdf`, там указан Python-плагин `GroundTruth` из `ground_truth.py`).

   Плагин получает основного робота вызовом `getFromDef('TURTLEBOT')`, а затем читает его позу через `getPose()`. Метод возвращает матрицу преобразования корневого объекта робота в глобальную систему координат сцены. Этот объект соответствует `base_link` в описании робота, которое экспортирует Webots. Скрипт извлекает положение и ориентацию, переводит вращение в кватернион и публикует `map → base_link_gt` через `TransformBroadcaster`. Этот же плагин публикует `/clock`.

   GT и колёсная одометрия образуют две ветки одного дерева:

   ```text
   map
   ├── base_link_gt
   └── odom
       └── base_link
   ```

   Статический `map → odom` совмещает начальную систему одометрии с глобальной системой сцены.

2. **Добавление шума.** В локальном `TurtleBot3Burger.proto` к исходному описанию добавлено поле `encoderNoise`. В обоих колёсных `PositionSensor` поле `noise` связано с ним строкой `noise IS encoderNoise`. Поэтому значение `encoderNoise` в файле сцены задаёт стандартное отклонение гауссовского шума показаний обоих энкодеров, в радианах. Шум добавляется к измеренным углам колёс, которые использует `ros2_control`.

3. **Расхождение без шума.** Даже при `encoderNoise 0` колёсная одометрия может не совпадать с GT. На результат влияют контакт колёс с поверхностью, проскальзывание, квантование и параметры кинематической модели. Для настройки можно использовать параметры контроллера `diffdrive_controller: 

- `wheel_separation`,
- `wheel_radius`,
- `wheel_separation_multiplier`,
- `left_wheel_radius_multiplier`,
- `right_wheel_radius_multiplier`.

   В примере для `diffdrive_controller` задан параметр `wheel_separation_multiplier = 1.1`. Это поправочный множитель расстояния между колёсами. Такое значение уменьшает расхождение, но не устраняет его полностью. Можно попробовать изменить его, чтобы улучшить точность запуска без шума. Фактическое значение проверяйте командой `ros2 param get /diffdrive_controller wheel_separation_multiplier`. Учитывайте, что множитель базы влияет и на расчёт одометрии, и на преобразование `/cmd_vel` в скорости колёс.

   Настройка не должна превращаться в отдельную задачу по поиску идеальных параметров. Если вы меняете их, сделайте это до основных экспериментов, зафиксируйте выбранные значения в `README.md` и используйте их во всех трёх запусках. Полное совпадение траекторий без шума не требуется.

1. Создайте собственный форк базового репозитория курса на свой аккаунт GitHub. Используйте один репозиторий для всех практических работ.
2. Для этой работы создайте отдельную ветку `practice-03` от исходной ветки `main`. Практические работы независимы, не создавайте ветку новой работы от веток предыдущих практик.
3. Разместите решение в папке `practices/practice-03`. Добавьте исходный код пакета, launch и остальные файлы, необходимые для сборки и запуска. В подпапку `results` добавьте изображения с результатами экспериментов.

5. Откройте `Pull request` из ветки `practice-03` в `main` **своего репозитория** (не используйте базовый репозиторий преподавателя). Запрос должен содержать изменения только по этой практической работе.
6. В заголовке запроса укажите `<ФИО, номер варианта>`.
7. Отправьте преподавателю ссылку на `Pull request` через форму сдачи. Не делайте merge веток до проверки вашей работы. Сохраните при этом ваш код до конца курса.

### Видеозапись

Запишите видео, на котором показаны:

- выбранное значение шума `encoderNoise 0.1`;

- завершение сбора данных и открытие сохранённого изображения с тремя графиками для этого запуска.

Команда запуска, значение шума и подписи на графиках должны быть читаемы. Видео должно соответствовать сдаваемой версии кода. Видео должно быть без посторонних действий, пояснения не обязательны.

Загрузите видео в облачное хранилище, откройте доступ для просмотра по ссылке и добавьте ссылку в форму сдачи. Сохраняйте доступ к репозиторию и видео до проверки решения.

### Сроки и проверка

Для оценивания используется последний коммит в ветке на момент проверки. Для применения мягких дедлайнов учитывается дата этого коммита (либо дата отправки формы, если это произошло позже): если после дедлайна в ветку добавлены изменения, работа оценивается с соответствующим ограничением максимального балла.

Время выполнения работы: 14 дней с даты проведения практического занятия.

Срок отправки:

- До основного дедлайна — максимальный балл без снижения.
- Не позднее 7 календарных дней после дедлайна — 75% от оценки.
- Позднее 7, но не позднее 14 календарных дней после дедлайна — 50% от оценки.
- Позднее 14 календарных дней после дедлайна — работа не учитывается в оценке за выполнение, если преподаватель заранее не объявил иной порядок.

Работа оценивается в представленном виде. Исправления и повторная проверка после выставления оценки не предусмотрены. Все сроки указаны по московскому времени (т.е. работа считается сданной, если она отправлена до 23:59 UTC+3 соответствующего дня дедлайна).
